# 根因升级(两轮补丁不收敛就停手)

## 何时触发

- 同一症状第二次复发(第一次修复后用户再报),或第二轮补丁实机验证仍失败。
- 机制类问题(提示词被复述/竞态/静默失败/对齐类 UI bug)通常**第一轮就该评估**是否直接上结构性方案。

## 规则

1. **停手**:不再写第三轮同层补丁(词表加词、措辞加禁令、加 try-catch 之类的层内追补)。
2. **复盘已试补丁**:列出每轮补丁是什么、为什么不够——要根因层的分析,不是「词不够多」。
3. **给结构性方案(2-3 个)**,每个写明:
   - 改动面(动哪些链路/数据层)
   - 行为影响(什么功能会变、什么体验会损失)
   - 风险与预估效果
   - 例(思维链复述):词表追补(现状,打地鼠)→ 提示词瘦身(减少可复述文本,动行为层)→
     机制工具化/纯后台化(改数据流,动架构)。
4. **交用户拍板**:未拍板前冻结该问题的补丁代码;拍板后执行,不再夹带其他改动。
5. **收尾**:把最终方案与教训写进 `.zcode/memory/`(lessons.md 踩坑、decisions.md 拍板),补丁追词的
   过程归档进对应 handoff。

## 为什么

结构性方案几乎都动行为层,用户不拍板就动手 = 重蹈 r264 模型劫持类事故(波及无辜路径);
而同层补丁两轮无效 = 该问题在当前层不可解,继续补只是消耗轮次和信任。
